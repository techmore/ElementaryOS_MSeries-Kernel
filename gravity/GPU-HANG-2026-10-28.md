# M4 GPU hang, 2026-10-28 (patch 0066)

Mac mini M4 (J773g) on Gravity 44 KDE, kernel `7.1.13-509.gravity.fc44.aarch64+16k`
(GravityLinux/linux pin `dea38a96`; its `drivers/gpu/drm/asahi` matches the series
source `4fc326f6`), Mesa `26.3.0~devel-103.gravity`, GPU firmware `mBoot-18000.161.10`,
4K HDMI display.

## Symptom

During normal desktop use (kwin, plasmashell, Brave) the GPU died three times in one
evening, once per boot (20:32, 21:07, 21:42):

```
asahi_m4: G16: submission pipeline failed: ETIMEDOUT, 128 jobs, 42 issued
asahi_m4: G16: failed to unbind closed GEM object: EIO
asahi_m4: G16: submission pipeline failed: EIO, 1 jobs, 0 issued   (repeated)
```

After that, every `SUBMIT` and `VM_BIND` returned EIO, and kwin, plasmashell and the
browsers aborted. None of the three logged `async Work … timeout without retirement
progress`, nor any firmware fault or timeout event.

## Cause

In the submission worker (`impl WorkItem for Execution`, `g16_drm.rs`), the loop
starts with `wake_result?`. When the previous `notifications.wait()` timed out (no
firmware notification within `watchdog_remaining_ms()`, up to 10 s), that line
returned ETIMEDOUT before `runtime.retire()` polled the completion stamps. The error
path poisons the runtime and sets `device.failed`, so one late or lost notification
kills the GPU until reboot, even when the work has finished.

GravityLinux/linux `replacement/210-gpu` (Linux 7.3 rebase, 2026-10-28,
`g16_drm_pump.rs`) already handles this. On a wait timeout it polls the stamps,
rescues finished work and logs it ("G16: rescue …"), and while work is in flight it
caps the wait at ≤250 ms. No packaged Gravity kernel contains that yet.

## Patch 0066

`patches/0066-drm-asahi-poll-M4-completion-when-a-firmware-notific.patch` backports
the minimal part to the 7.1 driver:

- ETIMEDOUT from the notification wait falls through to `retire()` instead of
  failing. A real 10 s stall still trips `retire()`'s watchdog, which now gets to log
  the stuck Work and context.
- `watchdog_remaining_ms()` waits at most 250 ms while any work is in flight.
- The first 64 rescues log `G16: notification wait timed out; polling retired Work …`.

Status: built as an out-of-tree module with Fedora rustc 1.98.1 (the kernel's
compiler) and running on the M4 since 2026-10-28 22:24. It loaded cleanly and the GPU
works. It has not yet been through a full hang window. How to read the log:

- `polling retired Work`: a lost notification was rescued (before the patch, a hang).
- `async Work … timeout without retirement progress`: a real GPU hang that this
  patch cannot fix.

`m4-module/` has the scripts used to build and install it on the running Gravity
kernel without rebuilding the whole kernel.

## Related findings on the same machine

- **Login screen with only a cursor:** `plasma-login` started before the HDMI output
  had modes, logged "There are no outputs", then quit on the hotplug, leaving kwin
  with only a cursor. This is unrelated to the GPU patch: it happened on the stock
  driver too. `m4-module/wait-display.conf` is a systemd drop-in for
  `plasmalogin.service` that waits up to 20 s for a connector to list modes.
- **Double unmap:** `UATPageTable::unmap_pages: Page at IOVA 0x2ffff90000 already
  unmapped` appears (4 lines, both page-table views) minutes before each hang, which
  suggests overlapping VM_BIND mappings. Not proven related.
- **kwin import failures:** `kwin_wayland_wrapper: import failed: Could not map fd N
  to handle` every few seconds (client dma-buf import fails).
- The firmware crash buffer (`0x100011dc000+0x8000`) has no debugfs or devcoredump
  reader in this driver.
